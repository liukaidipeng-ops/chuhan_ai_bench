# 楚汉拍板单与私有审批台复刻说明

编写：GPT · 2026 年 10 月 17 日  
用途：交给 Claude 重建可审材料、可追踪决定、可核查处理结果的私有审批台。本文是需求与实现说明，不是现有系统的源代码，不构成任何游戏上线授权。

## 1 阅读方式与事实边界

本文依据现有审批台在编写日的只读记录及已暴露的数据契约整理。实际记录确认了送审卡、批次提交、用户选项与备注、附图、一次性接手回执、制作排期和优先级。没有检查服务器源代码，也没有在本次任务中执行写入、审批、通知测试或发布。

以下三种标记贯穿全文：

- **已核实**：本次读到的实际记录或现有接口契约。接口提供能力不等于实际流程已端到端验收。
- **用户需求**：需要复刻的交互或业务目标，尚不能据此宣称现系统已经实现。
- **建议实现**：为了让重建版本可靠而提出的设计；字段、路由、数据库结构和算法均可调整，但不得改变审批语义。

公开文档只保留产品结构、通用规则和合成例子。真实私有审批记录、原始截图、用户备注、身份标识、聊天地址、访问凭证与私有素材链接不随文档公开。文中的示例编号、版本与 URL 均为合成占位，不能作为真实批准或发布证据。

## 2 产品目标与范围

拍板单让用户回答一个具体问题：这份候选是否接受，允许推进到哪一步。审批台负责保存材料、收集决定、展示处理过程及失败原因。发布执行器负责检查批准范围和当前权限、执行获准操作，并回填可验证证据。

初版覆盖八类制作职能：CG、技术、优化、美术、声音、数值平衡、角色、顾问。部门名称可配置；跨部门协调显示为独立工作流或角色，不应被硬编码成某个真实个人。原制作排期有任务编号、主责部门、协作方、状态、阻塞、验收证据要求、派发状态、优先级和提交快照。

原有业务要求是“先有可看的候选和材料，再让用户拍板”。生成候选包不能冒充真实验收通过；没有材料、材料不可读或只给一句“已优化”的任务，不进入正式待审批队列。缺真机测试时可以展示模拟环境的候选，但必须明确限制，且不能勾选真机验收通过。

## 3 页面信息结构

### 3.1 首页

从上到下建议安排：

1. 顶部：审批台名称、私有访问提示、数据最近读取时间、刷新与连接状态。
2. 待你处理：只列需要用户选择且材料已可读的事项，展示影响、建议、可操作按钮和关联卡片。
3. 部门进度：当前任务、阶段、产出链接、阻塞、下一步、最近进展时间、最近核验时间。
4. 送审列表：按待审、需修改、已批准待处理、处理中、已完成、已发布、暂缓或撤回筛选。
5. 历史记录：按编号、版本、部门、批次和时间检索。

“待你处理”不应塞满自动检查结果。对用户没有明确决策问题、缺可读材料或已解决的项目应隐藏出待办视图，历史仍保留。提醒时间与核验时间分开；刷新页面不会重新提醒用户。

### 3.2 拍板单卡片

卡片必须使用户在手机上也能看清以下内容：

- 编号、标题、部门、候选版本、基线版本、创建时间。
- 要用户决定什么；改了什么；本次包含和不包含什么。
- 候选材料、每份材料图注与来源说明、同条件前后对照。
- 已完成的检查、失败的检查、未进行的检查和环境限制。
- 每个选项的完整含义及允许的下一步。
- 备注输入、反馈图片、关联具体材料的标注入口。
- 提交前摘要、提交结果、批次编号和后续回执入口。

“已通过”必须同时显示通过的范围，例如“仅通过文案方向”或“仅通过该候选整合验证”。不要以一个绿色勾选覆盖所有业务阶段。

### 3.3 图片、动态材料与声音

已核实的现有上传规格为 PNG/JPEG/WebP 图片及 WebM/MP3/WAV/Ogg 音频，单文件上限 5 MB。重建可调整限制，但需在上传前告知并验证文件真实类型，不能仅检查扩展名。

建议视觉审核支持原图放大、前后图切换、逐张备注及标注。保存原图与标注结果为不同附件，记录父附件关系、坐标系、原始宽高和标注版本。旧附件缺少来源标记时显示“历史反馈图”，不能推定为原图或标注图。

GIF/视频是扩展需求。实现时记录对应构建与场景，支持暂停、关键时点和静帧回看，考虑手机带宽及自动播放限制。音频支持独立试听、停止、重播与时间位置。样片、程序截图、真实游戏截图、浏览器尺寸模拟及物理设备录像须有清楚标签。

不能播放动态材料时，显示同版本关键帧与可访问录像链接以及当前限制。静态图不能替代对动态衔接、声画同步、交互过程或真机温耗的验收。

## 4 可直接采用的拍板单模板

以下为合成模板，不是历史审批记录：

```text
编号：DEMO-UI-001-R2
标题：手机操作区候选第二版
部门：界面设计
候选：demo-build-002
基线：demo-baseline-001

请你决定：是否接受本版操作区布局。
本次改动：按钮等宽、增加文字留白。
本次范围：只涉及该操作区，不含玩法、声音或其他界面。
材料：同一候选的前后截图与交互录像。
材料性质：真实游戏在浏览器手机尺寸模拟；未做物理设备验证。
已检查：指定尺寸下选择、取消、返回及长文本显示。
未检查：物理设备触控与系统安全区，需后续补充。

选项 A：通过，整合验证
含义：认可候选并允许整合回归，不授权正式发布。
选项 B：不通过，需要调整
含义：按备注返工，制作新版本再送审。
选项 C：暂缓
含义：保留历史和当前正式版，暂不推进。

备注：请写具体图、区域、场景及期望结果。
```

若使用“通过并上线”，必须把选项 A 改为准确描述候选版本、批准范围、发布目的地和必要前置检查的发布选项。不得只改按钮文字，却仍让后端读取一个没有范围信息的布尔值。实际发布仍受当前有效权限和必要确认约束，历史按钮不能覆盖之后生效的约束。

## 5 决定、处理与发布的状态模型

建议拆成四条状态轴，避免一个 status 同时代表所有结果。

1. 卡片生命周期：草稿 → 可送审 → 已提交快照 → 被新版本替代或归档。
2. 用户决定：尚未提交、要求修改、暂缓、方向认可、整合批准、范围发布批准、已撤回。
3. 处理阶段：已接手、处理中、受阻、待复审、工作完成、已发布、已取消。
4. 通知阶段：待发送、平台接受、发送失败、结果未知、实际读取已确认。

现有处理契约包含 accepted、in_progress、blocked、awaiting_review、completed、published、cancelled。建议沿用兼容值，但将“工作完成”和“已发布”明确区分。部门状态的 phase_completed 只表示阶段完成，不表示全项目完成。

### 关键转移约束

- 上传材料、选中按钮和保存草稿均不构成提交。用户明确提交后才产生不可变的决定快照。
- 用户提交后不得悄悄修改原卡材料、选项或批准范围。修订产生新版本，并链接旧版；原记录保留。
- 要求修改后，执行者可以在已有授权内准备新候选；新候选需要重新送审，不继承旧版发布批准。
- 接手回执只能说明实际读到和接手的事实，不能写成已经修改、验证或上线。
- 受阻状态要写具体原因和下一步；恢复时追加新事件，不覆盖阻塞历史。
- 正式发布前核对当前有效决定、候选身份、目标与范围、必要测试和当前权限。无法核实任一项时停止发布并说明缺口。
- 只有远端发布证据与目标环境核查支持时才能写“已发布”。构建成功、提交成功、合并成功、部署排队或工具调用成功均不足以单独证明上线成功。
- 撤回在执行前阻断后续动作；执行中撤回应标记实际已执行边界并请求下一步。撤回不代表已上线内容自动回滚，回滚必须有独立授权与结果记录。

## 6 建议数据模型

以下是重建建议，不是现有内部 API。沿用已核实的业务概念，并增加防止错版本发布的显式字段。所有时间以带时区的 ISO 8601 保存，界面按用户时区显示。

| 实体 | 关键字段 | 不变量 |
| --- | --- | --- |
| ReviewItem | id、number、departmentId、title、description、kind、revision、candidate、scope、options、materialIds、createdAt | 编号稳定；提交后冻结该版 |
| Material | id、type、storageKey、mimeType、bytes、digest、caption、sourceKind、candidateVersion、parentId | 私有访问；标注不覆盖原件 |
| Submission | id、batchId、itemId、itemRevision、optionId、decisionSnapshot、note、attachmentIds、submittedAt、actorRef、withdrawnAt | 保存提交时的选项文本、范围和材料摘要 |
| Acknowledgement | submissionId、receivedAt、actorRef、message | 与用户决定分离，一次性接手回执 |
| ProcessingEvent | eventId、submissionId、stage、message、evidence、blocker、nextStep、createdAt、supersedesEventId | 追加写；更正指向旧事件 |
| DepartmentStatusEvent | eventId、departmentId、currentTask、stage、blocker、evidence、nextStep、statusUpdatedAt、verifiedAt | 核验不伪造进展 |
| PendingDecision | decisionId、eventId、title、action、impact、recommendation、materials、stage、verifiedAt、lastRemindedAt、resolution | 可读材料充足，确需用户决定 |
| ProductionSnapshot | id、tasks、priorities、version、submittedAt | 草稿与已提交优先级快照分开 |
| NotificationAttempt | id、eventId、destinationRef、state、attemptedAt、providerReceipt、readAckAt | 不把平台接受当作已读 |
| ReleaseAttempt | id、submissionId、candidateDigest、targetRef、state、evidence、verifiedAt | 范围与目标匹配；执行权独立校验 |

## 7 写入一致性与幂等

建议数据库为每次用户提交和处理事件建立稳定唯一键，客户端双击、断网重试或后台重放不会产生第二个决定、重复提醒或重复发布。相同键且相同内容返回原结果；相同键而内容不同应报冲突，不能静默覆盖。

批次提交用事务保存所有选中事项的版本快照与批次摘要。提交前校验材料仍可读、卡片版本仍一致、选项仍有效；遇到版本变更，展示差异让用户重看。对未选择项不生成决定，提交失败时不显示成功。

先提交决定事务，再通过持久化待发送队列投递通知；通知失败不能回滚已保存的真实决定。使用事件唯一键去重消费者，记录重试次数和结果，失败进入可检查的失败队列。不要声称跨服务“绝对只执行一次”；应以持久化状态、互斥锁、幂等业务键和结果核对避免重复副作用。

结果未知时先按稳定键查询既有记录。若已成功则读回原结果；若明确未写入才重试；若仍未知则保留“待核实”并阻止可能重复的发布。更正处理状态追加 supersedesEventId，原事件不可被删除或重写。

## 8 通知与聊天备用审批

通知链路要能区分四个事实：决定已保存、通知已尝试、平台已接收、执行者实际已读。当前连接正常也不能证明任何一条具体通知送达或被处理。

用户提交后页面立即显示保存结果与批次编号；执行者实际读取后才追加接手回执，并在已有授权的用户聊天渠道同步简短结果。页面“待你处理”本身不应被描述为已经发出提醒。

通知失败或结果未知时，页面保留决定并显示明确状态和“复制审批摘要”入口。用户可在私有聊天中引用卡片编号、版本、具体选项和范围完成备用确认；执行者需核实聊天确为用户本人及决定适用的候选。聊天决定作为关联的新审计记录，不能伪造用户在网页点过按钮，也不能仅凭第三方转述执行发布。

发生网页与聊天冲突时保留两条来源和时间，核实用户最新有效决定；不能自动挑选更宽的授权。没有明确发布权限时，只能处理已获准的部分。通知测试卡必须写明只测试通知，不允许触发游戏操作。

## 9 部门进度与点击核验

已核实的状态契约区分 statusUpdatedAt 和 verifiedAt：前者只在任务、产出、阻塞或证据真实变化时更新，后者表示最近核查时间。当前契约以超过 15 分钟未核验标记“待核实”，不直接判定停工或发呆。

重建时保留这个区分。用户点核验后展示“正在核查”，读取实际任务与证据；内容未变只更新核验时间，内容变化才追加状态事件及进展时间。请求失败显示失败与旧数据时间，不用当前时间伪装刷新成功。

部门卡建议同时展示“最近进展”和“最近核验”。暂停、阻塞、待用户决定、工作中及阶段完成各有独立文案。某部门阶段完成不应自动把其他关联任务、用户验收或发布标为完成。

## 10 私有访问与审计要求

审批台与素材应要求认证，不因页面 URL 难猜就称为私有。服务器校验访问者与事项归属，不能信任浏览器传来的 owner、department 或 approved 字段。提交用户决定的身份必须可验证；执行者可以追加进度，但不能冒充用户作决定。

建议最小权限分离：用户审批角色、部门送审角色、协调者状态角色、发布执行角色。即便单人使用也要保留逻辑边界。发布凭证不进入网页、公共仓库或审批附件。历史素材的读取继续执行归属检查；过期链接可重新生成，但不能因此修改历史内容。

审计记录包括主体引用、时间、关联卡片与版本、动作、结果和证据摘要。避免把凭证、私密聊天全文或无关个人信息写入日志。对备注做转义，对文件做大小与类型限制，对上传路径防遍历，对服务端抓取链接限制目的地，写接口具备适用的防跨站请求措施。

这是追加式业务审计设计，不应在未实现防篡改存储前宣称记录绝对不可篡改。备份、导出和恢复需有实际测试；公开演示环境只能使用合成数据。

## 11 给 Claude 的实施顺序

1. 建立上述实体、版本与约束，先写数据库和业务层测试。
2. 实现私有登录、部门列表、送审卡、静态图片与音频材料。
3. 实现手机可用的选项、备注、反馈图、批次提交与历史读取。
4. 实现一次性接手回执、追加处理事件、部门状态及待你处理。
5. 接入通知队列、失败状态和聊天备用流程，做真正端到端测试。
6. 在独立测试环境接发布适配器；默认关闭真实发布，先验证范围门禁和重复调用保护。
7. 增加 GIF/视频、图像标注和高级筛选，并标记各项实际验收情况。

技术栈可自选；持久化存储必须支持原子写入或等效一致性保证，素材应独立私有存储。不要把公共静态站点里的 JSON 文件当成私有数据库。复刻完成须交付运行说明、配置变量名称、迁移脚本、合成样例、测试命令、验证报告与已知限制。不得提交真实密钥或真实用户数据。

## 12 验收清单

### 业务正确性

- [ ] 只生成候选时仍显示未验收；模拟截图不显示为物理设备测试。
- [ ] 两个同名 pass 选项因批准范围不同，产生不同权限结果。
- [ ] 整合批准不触发发布；发布批准仅覆盖卡片指定候选和范围。
- [ ] 已提交材料和选项不可原地替换；新版需重新确认。
- [ ] 要求修改、暂缓、撤回、复审和归档均保留历史。
- [ ] 已接手、工作完成、部署排队、发布已验证显示不同状态。

### 失败与重复

- [ ] 双击提交及网络重放只生成一个有效提交。
- [ ] 相同事件键不同内容产生冲突，同内容返回原结果。
- [ ] 批次中一项版本过期时不留下误报成功的部分提交。
- [ ] 通知失败仍能读到已保存决定，页面显示失败。
- [ ] 平台接受而没有读取回执时不显示“已查收”。
- [ ] 超时后先查既有结果，不盲目重复发布。
- [ ] 撤回与执行同时发生时有可核实边界，不声称自动回滚。
- [ ] 追加更正保留原事件并能追踪关系。

### 界面与素材

- [ ] 桌面与窄屏手机可读，长标题、长备注、横屏及大字号不挡审批按钮。
- [ ] 上传失败、素材过期、音频不可播放、动态材料不支持均有可理解提示。
- [ ] 图片放大、标注回看、退出与重复打开不丢未提交反馈。
- [ ] 刷新、返回、重复导航不会误提交或丢失已保存决定。
- [ ] 核验成功但没有进展时，只改变核验时间。
- [ ] 超过核验时限显示待核实，而非未经证实的停工结论。

### 安全与发布

- [ ] 未认证、跨用户、跨部门越权请求被服务器拒绝。
- [ ] 真实用户决定不能由普通执行账号伪造。
- [ ] 素材 URL 与历史附件执行私有访问检查。
- [ ] 发布门禁检查候选摘要、当前决定、范围、目标和必要权限。
- [ ] 发布成功后保存远端版本及目标验证证据；失败保留阻塞。
- [ ] 公共仓库、示例、日志与测试夹具不含真实私有记录或凭证。
- [ ] 备份恢复后历史决定、素材关联和幂等键仍一致。

## 13 交付判定

本说明文档的完成不代表审批台已经重建或游戏已经上线。Claude 的完成报告应列出：已实现能力、执行过的测试、未覆盖的检查、部署目标及其验证状态、尚需用户决定的问题。任何只有接口、没有真实闭环测试的能力都应如实标为待验收。

验收优先检查三件事：用户看见的材料是否对应被批准的候选；后台做的事情是否落在该批准范围内；最终回执是否有实际证据。三者能连续核对，拍板单才可用于真实制作流程。
